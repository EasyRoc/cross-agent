# 商品分析系统优化实施方案（Spec + Plan）

> 基于 2026-10 全链路代码审查（前端 5 个文件 + 后端全部模块）得出的问题清单，
> 按优先级整理为四个实施阶段。每项含问题根因、技术方案、涉及文件与验收标准。

---

## 1. 背景与目标

### 1.1 审查结论

系统正常路径（登录 → 发起分析 → 12 维分析 → 概览确认 → 报告下载）功能完整，
但**异常路径几乎全线失守**：

- 前端出错即卡死（流断开、决策失败、终止操作三条路径均进入不可恢复状态）
- 后端出错即静默降级（Milvus / Tavily / 百炼的失败被吞成空列表，上层无感知）
- LLM 降级方案在真实故障场景下大概率不可用（三处实质缺陷）
- 同步 I/O 阻塞事件循环，单个慢请求拖垮全部并发会话

### 1.2 目标

1. 修复所有确定性复现的功能 bug（P0）
2. 建立异步纪律，解除事件循环阻塞，治理 SQLite 并发（P1）
3. 补齐安全短板（P0 内）与数据质量兜底（P2）
4. 完善交互体验，重点修复 HIL 决策流程的状态机（P0 + P3）

### 1.3 非目标（本方案不做）

- 不改变整体架构：保留 LangGraph Supervisor 模式、SSE + REST 协议、现有目录结构
- 不引入前端框架（Vue/React），继续纯静态实现
- 功能增强（报告图表、OSS 上传、SKILL、长期记忆）仅做衔接设计，按
  [需求优化计划](需求优化计划.md) 原方案另行排期

## 2. 阶段 P0 — 确定性缺陷修复

> 预估 2-3 人日。目标：用户一次正常使用就会撞上的问题全部修复。

### P0-1 PDF 报告路径与下载修复

**问题**：`app/api/chat.py:293-296` 只把 Markdown rename 进用户目录，PDF 从未移动，
但 `chat.py:303` 把用户目录下不存在的 PDF 路径写入任务记录。结果：认证用户 PDF
下载必然 404；所有 PDF 实际滞留在 `reports/` 根目录，可经无鉴权的 `/download/{filename}`
端点（`chat.py:392`）被任何人下载。

**方案**：
1. Markdown 与 PDF 统一移动到 `reports/{user_id}/`（move 失败时报错并置任务为 failed，
   不允许半成品标记 completed）
2. PDF 生成失败时 `report_pdf_path` 置空字符串，不得以 `.md` 路径冒充
   （`app/report/generator.py:108-110` 现有回退逻辑一并移除）
3. 保留 `/download/{filename}` 仅供调试（加 `resolve()` 目录约束，见 P0-4），
   正式下载一律走 `/api/tasks/{id}/download/*`

**涉及文件**：`app/api/chat.py`、`app/report/generator.py`

**验收**：
- 登录用户对同一任务 md / pdf 均可下载且内容正确
- 未携带有效 token 无法下载任何用户目录下的报告
- 文件系统检查：`reports/` 根目录不再堆积 PDF

### P0-2 LLM 降级链路修复（三处缺陷）

**问题**：
1. `app/llm/client.py:66` `_resolve_model` 中 `if model: return model` 直接返回百炼模型名，
   而概览生成（`overview_generator.py:63`）、报告生成（`report_generator.py:62`）、
   意图识别（`chat.py:108`）均显式传参 → 降级后这些请求拿 `qwen-max` 打 Ollama，404
2. `client.py:20-29` 把 `RateLimitError`（429 限流，瞬时）与 402 额度枯竭同等对待，
   一次抖动即全局永久降级且永不回切（`client.py:121`）
3. 降级后 embedding 走 Ollama `dengcao/Qwen3-Embedding-4B`（2560 维），Milvus 集合为
   1024 维（`app/rag/milvus_client.py:68`），维度不匹配异常被吞成空列表 → RAG 静默失效

**方案**：
1. **模型映射表**：新增 `{百炼模型名: Ollama 模型名}` 映射（`qwen-plus/qwen-max → settings.ollama_model`，
   `text-embedding-v3 → settings.ollama_embedding_model`），`_resolve_model` 在降级态查表转换，
   调用方无需改动
2. **降级条件收紧**：仅 `error.code == "insufficient_quota"` 或 HTTP 402 触发永久降级；
   429 限流做 2 次指数退避重试（1s / 3s），仍失败才抛错给上层。降级态增加"冷却恢复"：
   距降级超过 `fallback_cooldown_minutes`（默认 60，可配）后下一个请求试回百炼，成功即回切
3. **维度协商**：`MilvusClient` 建集合时把实际使用的向量维度写入集合描述并在内存缓存；
   `hybrid_search` 检索前比对当前 embed 输出维度，不匹配时输出**明确告警日志**
   （"embedding 维度 X 与集合维度 Y 不匹配，RAG 已跳过"）并跳过 RAG 源（其余源正常），
   不再静默吞异常

**涉及文件**：`app/llm/client.py`、`app/rag/milvus_client.py`、`app/rag/hybrid_search.py`、`app/config.py`

**验收**：
- 清空 `DASHSCOPE_API_KEY`（模拟额度枯竭）后，意图识别 / 闲聊 / 分析 / 概览 / 报告
  全流程走 Ollama 跑通
- 模拟 429（不模拟 402）时百炼仍为主后端，日志可见退避重试
- 降级状态下发起分析，日志出现维度告警，任务不失败（Tavily/LLM 兜底源正常）

### P0-3 前端错误路径死锁修复

**问题**（均位于 `static/app.js`）：
1. 流读取 catch 只 `console.error`（`app.js:113-115`）→ 断网后 typing 残留、
   `isProcessing` 永久为 true、输入框永久禁用
2. terminate 用 fire-and-forget fetch，后端从不下发 `terminated` 事件 → 终止后界面死锁，
   `case 'terminated'`（`app.js:197`）为死代码
3. confirm/reject 先隐藏概览卡再发请求（`app.js:264,282`）→ 请求失败（含 401）后
   概览卡消失、后端仍在等待决策，无任何恢复入口
4. confirm/reject 无防重复提交（`app.js:263-293`）→ 双击第二次必报错并触发上一条

**方案**：
1. **统一收尾函数** `recoverFromStreamError(message)`：移除 typing 指示器、
   `setProcessing(false)`、渲染错误气泡。SSE 读取的 catch 与 `finally` 都调用
2. **决策请求改造**：先置按钮 loading（禁用），请求**成功**后再隐藏概览卡；
   失败时恢复按钮可用、概览卡保留、弹错误提示可重试
3. **terminate 改走 `/api/chat/decide`**（action=terminate，后端已支持且返回 SSE），
   废弃对 `/api/chat/terminate` 的直接调用；收到流结束即复位侧边栏与输入区
4. 所有决策 / 发送入口统一检查 `STATE.isProcessing` 与按钮 disabled 态

**涉及文件**：`static/app.js`、`static/index.html`（概览卡按钮结构微调）

**验收**：
- DevTools 断网模拟：流中断后输入框恢复可用，出现错误气泡
- 决策接口返回 500 / 401 时概览卡仍在，可重试或终止
- 快速双击确认只发出一次请求

### P0-4 安全加固（三件事）

**问题**：
1. `app/agent/nodes/report_generator.py:71` 用 LLM 提取的商品名直接拼报告文件名，
   含 `../` 或 `/` 可写到 reports 目录之外（任意文件写）
2. `/download/{filename}`（`chat.py:392-400`）无目录约束校验
3. `/api/chat/decide`、`/api/chat/terminate`（`chat.py:352-381`）无鉴权、不校验任务归属，
   知道 session_id 即可操作他人分析

**方案**：
1. `report_generator` 新增 `sanitize_filename()`：仅保留中文/字母/数字/`-_`，
   其余替换为 `_`，并限制长度 ≤ 80 字符
2. `/download` 与报告保存统一走 `Path.resolve()` + `is_relative_to(report_dir)` 校验
3. decide / terminate 解析 `Authorization` header（复用 `_resolve_token` + `get_user_by_token`），
   校验 snapshot 中 `user_id` 与当前用户一致，不一致返回 403

**涉及文件**：`app/agent/nodes/report_generator.py`、`app/api/chat.py`

**验收**：
- 商品名注入 `../../etc/passwd` 时报告正常落在 reports 目录内，文件名已消毒
- `GET /download/..%2Fapp%2Fconfig.py` 返回 404
- 用户 A 的 token 决策用户 B 的 session 返回 403

## 3. 阶段 P1 — 异步与并发治理

> 预估 2-3 人日。目标：解除事件循环阻塞，会话与任务可承受并发、可跨重启恢复。

### P1-1 同步 I/O 移出事件循环

**问题**：以下同步调用全部跑在 async 函数里，单个慢调用冻结全部在线会话：
Tavily requests（`app/mcp/tavily.py:125`，且初始化未传 timeout）、pymilvus gRPC
（`app/rag/hybrid_search.py:71`，每次检索还重复 `collection.load()`）、
weasyprint 渲染与文件写（`chat.py:285-286` → `generator.py:46,106`）、SQLite 全家
（`chat.py`、`user_api.py`、`auth/__init__.py`）。

**方案**：
1. Tavily / pymilvus / weasyprint / 文件写统一 `await asyncio.to_thread(...)` 包裹；
   Tavily 初始化补 `timeout=20`
2. `milvus_client` 增加连接复用与 `load()` 幂等（已加载则跳过）
3. Ollama embed 的 httpx 客户端改为模块级复用（`client.py:210` 每次新建）

**验收**：压测场景（一个会话生成 PDF + 另一会话普通对话）下普通对话首 token 延迟
不受明显影响（< 2s）。

### P1-2 SQLite 治理

**问题**：每次操作新建连接并重跑建表 DDL（`manager.py:62-77`，热路径
`_update_task_progress` 每个图节点事件触发一次）；未开 WAL / busy_timeout，
并发下 "database is locked"；`create_task` 先查后插存在 TOCTOU 竞态
（`manager.py:104-114`），并发可产生双活跃任务。

**方案**：
1. TaskManager / auth 收敛为进程内单例连接，DDL 仅首次执行
2. 连接参数：`PRAGMA journal_mode=WAL`、`PRAGMA busy_timeout=5000`
3. `create_task` 改为单事务内 `INSERT` + 唯一约束校验（部分唯一索引
   `CREATE UNIQUE INDEX ... ON tasks(user_id) WHERE status IN ('pending','running')`），
   捕获 `IntegrityError` 转"已有进行中任务"错误
4. 同步调用统一 `asyncio.to_thread` 包裹（或引入 aiosqlite，二选一，倾向前者少加依赖）
5. `update_task` 列名白名单校验（`manager.py:129-134` 现为 f-string 拼接）

**验收**：并发 5 个登录会话同时发起分析，无 locked 报错、无双活跃任务。

### P1-3 Checkpoint 持久化

**问题**：`app/agent/graph.py:141` 使用进程内 `MemorySaver`，服务重启后所有等待决策的
会话报废（interrupt 状态丢失），任务永久停在等待态。

**方案**：替换为 `langgraph-checkpoint-sqlite` 的 `AsyncSqliteSaver`
（`data/checkpoints.db`），`pyproject.toml` 增加依赖。thread_id 仍用 session_id。

**验收**：分析到"等待决策"态 → 重启服务 → 决策请求正常恢复执行并产出报告。

### P1-4 会话状态恢复接口

**问题**：前端 `session_id` 只存内存（`static/app.js:32-37`），刷新即丢；
等待决策的分析刷新后前端永远接不回（配合 P1-3 才能完整生效）。

**方案**：
1. 后端新增 `GET /api/chat/session/{session_id}`（需鉴权 + 归属校验）：
   返回 `{state: "idle" | "waiting_decision", overview: {...}, task_id}`，
   数据来源为 `graph.aget_state(config)`
2. 前端 `session_id` 持久化到 `sessionStorage`，页面加载时调用恢复接口，
   `waiting_decision` 态重建概览卡

**验收**：分析到概览确认 → 刷新页面 → 概览卡自动恢复，决策流程可继续。

## 5. 阶段 P3 — 交互体验优化

> 预估 3-4 人日。目标：把 HIL 决策流程做成可信的状态机，细节交互对齐真实使用习惯。

### P3-1 结构化进度事件（维度级）

**现状**：进度条靠 `includes('采集')` 中文子串匹配后端文案（`app.js:344-368`），
后端改词即静默失灵；12 维并行分析只有一条汇总文案，用户在数分钟等待中无反馈。

**方案**：
1. 后端采用 LangGraph 自定义流事件（`stream_mode` 增加 `custom`），
   `analyzer.py` 内 `as_completed` 逐维度发射 `{dim, status}` 事件
2. SSE 协议新增事件（写入 README）：

   ```text
   event: stage       data: {"step": "collect|analyze|review|overview|report", "detail": "..."}
   event: dimension   data: {"name": "配色", "status": "done|failed", "index": 3, "total": 12}
   ```

3. 前端按 `stage` / `dimension` 事件渲染侧边栏进度清单（对齐需求计划文档 4.2 节的布局），
   彻底移除子串匹配

**验收**：分析期间侧边栏逐维度点亮；后端文案任意改动不影响进度渲染。

### P3-2 输入与反馈细节

| 问题 | 方案 |
|------|------|
| Enter 发送未处理 IME 组合态（`app.js:571`） | keydown 检查 `e.isComposing` |
| 密码框回车双重提交（`login.html:103,192`） | 移除 keydown 监听，仅保留 form onsubmit |
| 注册成功后仍停留注册模式（`login.html:169-170`） | 修正 `isRegisterMode` 取反逻辑 |
| reject 反馈 placeholder"可选"实则必填（`index.html:96`） | 二选一：空反馈允许（等价"重新分析"）；或 placeholder 改为"必填"并给出提示文案 |
| 逐 token `textContent +=` O(n²) 且强制滚底（`app.js:132,521`） | 滚动聚合（rAF 节流）+ "用户上滑时暂停滚底，出现回到底部按钮" |
| 401 两套处理不一致（`app.js:64-73` / `tasks.js:48`） | 统一 `handle401()`：清 token → 跳登录页带 return URL |
| 报告下载带 `?token=` 进浏览器历史 | 前端改 fetch + blob 下载，`Authorization` header 携带；后端 `?token=` 参数保留兼容一版后移除 |

### P3-3 状态与生命周期

| 问题 | 方案 |
|------|------|
| 长分析期间无取消入口（`index.html:100`） | 侧边栏分析中常驻"终止分析"按钮（走 decide/terminate），确认弹窗防误触 |
| 登出清理不完整（`tasks.js:159-162`） | 登出停轮询、复位侧边栏与 STATE、清 sessionStorage |
| 暗色模式：登录页不生效、主页刷新闪白（`login.html:92`、`index.html:2`） | 主题初始化脚本前置到 `<head>` 内联执行（两页统一） |

| 任务分页有接口无 UI（`tasks.js:58`） | 列表底部"加载更多"按钮接通 `page` 参数 |
| 移动端 100vh 与安全区（`style.css:53,62`） | `100dvh` + `env(safe-area-inset-bottom)`；概览操作按钮在移动端吸底 |
| 多标签页状态不同步 | 监听 `storage` 事件：token 变化时同步登出态 |

### P3-4 XSS 加固

商品名与 LLM 返回值经 innerHTML 插入（`app.js:406,438`）→ 全部改 `textContent` /
复用 `tasks.js` 的 `escapeHtml`；与 P0-4 的服务端消毒配合形成两层防护。

## 7. 里程碑与排期

| 阶段 | 内容 | 预估 | 里程碑验收 |
|------|------|------|-----------|
| M0 (P0) | 确定性缺陷 + 安全加固 | 2-3 人日 | 断网/失败场景 UI 可恢复；Ollama 全流程跑通；PDF 可下载；路径遍历/越权被拒 |
| M1 (P1) | 异步治理 + 持久化 | 2-3 人日 | 并发压测无阻塞无 locked；重启后会话可恢复 |
| M2 (P2) | 数据质量 | 1-2 人日 | 任务状态可信；LLM 异常均有兜底与告警 |
| M3 (P3) | 交互体验 | 3-4 人日 | 维度级进度可见；登录/刷新/登出/多标签全场景无死态 |

**总计约 8-12 人日**。每个阶段独立提交、独立可回滚；P0 完成即建议部署一次验证。

## 8. 测试策略（新增建议）

当前项目零测试覆盖（README P3 规划项）。本方案要求每阶段附带最小回归：

1. **P0**：`pytest` + `httpx.AsyncClient` 冒烟——注册/登录/发起分析 mock LLM 的端到端用例、
   文件名消毒单测、鉴权 403 用例
2. **P1**：并发创建任务竞态用例；`to_thread` 包裹后的超时用例
3. **P2**：价格解析 / chat_json 重试 / 状态机单测
4. **前端**：暂不引入测试框架，用浏览器手动走查清单（本方案各验收项即清单）

## 9. 风险与缓解

| 风险 | 说明 | 缓解 |
|------|------|------|
| 降级行为变化 | 429 不再立即降级，百炼限流时延迟上升 | 退避参数可配；日志观测降级率 |
| AsyncSqliteSaver 新依赖 | langgraph-checkpoint-sqlite 版本兼容 | 锁定版本；启动时 schema 检查 |
| 质量审核回退成本 | P0 恢复回退后，回退 = 重新采集 + 12 维全量重跑 | `max_quality_retries` 默认 2 可调；P2/P3 考虑"只重跑低分维度"优化 |
| 前端改动面广 | P3 涉及多数交互代码 | 按 P3-1 → P3-4 分小步提交，每步手动走查 |
